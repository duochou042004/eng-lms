# ADR-0001: Modular monolith with Spring Modulith

- Status: Accepted (baseline) · Date: 2026-09-25 · Deciders: LC · Trace: SPEC §35, §36, §54; PO directive (modular monolith)

## Context
There is one tutor, ≤ 200 students and one host (A-001). SPEC §35 recommends a modular monolith and forbids microservices without evidence. The PO wants the
backend to be "modular, replaceable and scalable without premature distributed complexity". Coding agents erode boundaries
unless something enforces them mechanically.

## Decision
One Spring Boot application. Top-level packages under `com.englms` are **Spring Modulith application modules** (module list in
`module-boundaries.md`). Boundaries are verified by `ApplicationModules.verify()` in a unit test that runs in CI. Cross-module
side effects use Spring Modulith application events with the JDBC event publication registry. Module docs (C4/PlantUML) are generated by
the Modulith `Documenter` into `docs/03-architecture/generated/` at milestone ends.

## Alternatives considered
- **Microservices:** rejected (SPEC §35/§36; operational cost for a single tutor).
- **Plain packages + ArchUnit:** workable, but Modulith adds event reliability and module-scoped integration tests for little cost.
- **Maven multi-module:** stronger compile-time isolation, but more build friction. It can be adopted later without changing module APIs.

## Consequences
+ Mechanical boundary enforcement. Modules can be extracted later if evidence demands it. One deployable, easy to debug.
− Developers and agents must learn the Modulith conventions (named interfaces, the `internal` packaging). They are documented in module-boundaries.md.
Follow-up: verify the Boot 4.1-compatible Modulith version in T-M1.2.

## Verification
`ModularityTests.verify()` passes in CI. A deliberately illegal dependency in a spike commit makes it fail (evidence T-M1.2).
